# Generated linked-workload Base baseline

This S1.0 tool uses the unchanged `zorid-s1-workload-v1` files, the actual Rust
Markdown/index generation and current Base compiler/query interfaces. It introduces
no engine/cache/language change. The [small semantic corpus tool](BASES.md) remains
a separate gate; this tool adds independent arithmetic expectations over the
100-note smoke and 10,000-note representative profiles.

Build/run only under the coordinator's serialized resource slot. The example is
`crates/zorid-bases/examples/s1-generated-baseline.rs`; a matching build is
`cargo build --offline --locked --release -p zorid-bases --example
s1-generated-baseline --jobs 1`. The wrapper accepts that already-built artifact
and never runs Cargo.

```sh
node scripts/indexing-search-baseline/generated-bases.mjs \
  --out /private/tmp/zorid-s1-generated-bases-UNIQUE \
  --bases /absolute/path/to/already-built/examples/s1-generated-baseline \
  --notes 100 --timeout-ms 60000 \
  --build-sha EXACT_40_CHARACTER_SOURCE_SHA --build-mode release
```

Start with genuine 100-note correctness. A later granted pass uses `--notes 10000`.
Other sizes, including 100k, are outside this bounded tool. Destinations must not
exist. The wrapper uses private permissions and retains all inputs, raw NDJSON and
`generated-bases-report.json`. It validates fixed profile manifest hashes, every
source length/digest before/after the child, captured plan bytes and executable
pre/post hashes. Only exact owned child processes may be terminated on failure.

## Five programs, eight invocations

Programs are host-fed benchmark requests; they do not rewrite either frozen Base
file or invent a new Base language. The sparse program uses the exact existing
`sparse.base` bytes. Other configurations are JSON mappings accepted as YAML by
`compile_base_source`. Their definitions and arithmetic oracles are versioned in
`generated-bases-oracle.mjs`; no expected value is generated by an evaluator.

| Invocation | Expected semantics |
| --- | --- |
| Sparse, then unchanged repeat | Existing `rank < 100`: first 100 notes in ascending name/rank order; identical row/cell/count oracle on both calls |
| Formula/sort/group | `0 <= rank < 100`, doubleRank=2×rank, rank descending; status groups doing/done/todo with exact typed keys and i mod 3 membership |
| Relationship filter | Same rank range plus one outgoing link: even note indices; links[0] targets note i+1 with its exact identity/revision and rooted link spelling |
| Current0/ascending | First ten ranks, formula this.rank=0, ascending view |
| Current1/ascending | Same membership/order, this.rank=1 |
| Current1/descending | Same current entry, reversed rank order and the distinct selected view |
| Fixed clock | First three ranks, today().toString()="2024-01-15" from the pinned accepted clock-pinned fixture's exact clock/UTC context |

Each success checks complete ordered row identities/revisions, declared typed
cells, counts, properties, groups and members, no unexpected diagnostics, and the
single explicit Binary PNG metadata issue. Returned rows are bounded to at most
100. Supplemental hashes retain actual full typed results but are not independent
oracles for unasserted cells. The clock example's accepted source hash/context are
checked separately. Repeated/context/view invocations use one already compiled
program object; this does not prove a new cache, invalidation strategy or hit rate.

## Full workload, budgets and incomplete outcomes

All notes, two Base files, one binary attachment and every original link remain in
one genuine `GenerationBuilder` generation. No links are dropped, source corpus
shrunk, work ceilings raised or detached snapshot substituted. Fixed synthetic
presentation facts come from the manifest and bind to exact input revisions. Pure
fixture source/epoch tokens are benchmark identities, not storage edit capabilities.

The current `query_generation` always prepares the complete relationship snapshot,
including for a property-only filter. `graph.rs` calls `ResolutionView::snapshot_checked`;
`relationships.rs` invokes `Resolver::candidates_checked` per link. That resolver
charges at least the namespace size for each edge and performs namespace scans.
For frozen 10k input, 5,000 links × 10,003 entries already implies 50,015,000 minimum
resolver work versus the current 2,000,000 query ceiling. This is source inference,
not an observed run or a measured counter. The separate generation metadata and
scan ceilings still apply.

The tool records actual outcomes individually. A budget error is never zero
matches or successful full-query latency. Its report field is
`elapsedToRejectionMs`, with semantic correctness unestablished. Pure read-only
query errors can be recorded before continuing to the remaining bounded requests.

- All successful results must satisfy their frozen arithmetic oracle.
- Any rejection on the 100-note correctness profile fails the pass.
- A 10k pass containing only supported `budget` rejections and valid successful
  results is `limited-incomplete`, exits nonzero and establishes no passed complete
  performance gate. Other rejections/protocol errors are `failed-or-incomplete`.
- A future genuine 10k success must satisfy the same original semantic expectations;
  the current engine is not asked to manufacture those expected outputs.

The accepted later optimization seam is dependency-aware graph preparation,
indexed resolution preserving normalization/tie semantics, and bounded reuse of
exact-generation preparation. This tool implements none of them. Complete S1.0,
S1.1/S1.2 changes and client performance require separate acceptance.

## Measurement and resource scope

Source read/UTF-8 setup is separate from generation construction, YAML/configuration
compilation, query outcome and result encoding/output. Generation construction
includes parser work, digest verification, witness binding, current record clones
and insertion. Rust verifies text commitments through the actual index record
digest; binary body hashes are the wrapper's before/after check. Binary exclusion
does not claim body search/OCR. Query time includes current graph/adapter/evaluator
preparation and internal budget accounting. No unmeasured cache/queue/RSS/CPU values
are reported as zero. OS cache and machine load remain uncontrolled.

Bounds are 64 MiB manifest, 1 MiB plan, 16 MiB single source, 128 MiB aggregate source,
128 MiB stdout, 16 MiB NDJSON record and 1 MiB stderr, plus the owned process timeout.
Current parser/generation/query limits remain intact. Source/captured requests and
executable identity failures retain failed reports. No persistent database, native
import, renderer, browser or mobile runtime is exercised.

Lightweight checks, requiring no Rust execution or timing workload:

```sh
node --check scripts/indexing-search-baseline/generated-bases.mjs
node --test scripts/indexing-search-baseline/generated-bases.test.mjs
```

Synthetic protocol tests distinguish limited rejection from correctness success
and reject altered order, values, groups, targets, contexts, source witnesses,
options, counts and final sequencing. They do not stand in for actual 100/10k runs.
