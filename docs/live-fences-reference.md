### Copy newline contracts

Reading and Live do not start from the same representation in the pinned source. Reading's HTML code element has a renderer-added terminal LF; its `Nj` helper removes that structural LF. `readCodeFence` already returns a normalized body, so Reading copying must not trim it again. For opener / `a` / blank line / closer, Reading copies `a\n`.

The Live block branch calculates the body using the first content line's `.from` through the last content line's `.to`, and the `Z5` flair nevertheless removes one terminal LF. For the same example, the statically observed Live branch copies `a`. This module preserves that explicit Live behavior rather than silently substituting improved semantics. A native reference clipboard comparison remains required; tests distinguish the two contracts and do not mistake the Reading repair for a Live parity requirement.

## API and integration handoff

New modules are independent of editor/workspace routing.

- Import `liveFences` from `src/editor/live-fences.ts` and install in the **Live Edit** extension list alongside the existing Markdown parser. Import `src/editor/live-fences.css` once in application CSS setup. Existing inline/embed scanners already exclude `FencedCode`; do not add a second source renderer.
- `liveFences({ highlight?, copyText?, onError?, handledLanguages? })` accepts a host clipboard/error policy and optionally a specialized-language ownership set. The default highlighter uses the worker below; tests can inject a token service.
- Reading: replace the existing naive fence branch with `readCodeFence(lines, position)`. On success, call `appendCodeBlock(container, parsed.code, parsed.info, options)` and advance to `parsed.endLine`. The helper recognizes matching marker kind, sufficient closing length, close-line whitespace, up-to-three-space indentation and unclosed fences. Recursive list/quote renderers should provide already parsed code content instead of calling this top-level adapter on prefixed lines.
- `appendCodeBlock` returns `{ element, ready, destroy }`. The host **must call `destroy()` before replacing/removing the owning reading surface**, or call the exported `destroyCodeBlocks(container)` helper to dispose all nested block owners. It aborts work, disconnects the lazy observer, settles readiness and cancels clipboard feedback. `ready` settles when highlighting completes/fails or ownership ends; it can remain pending while the block is offscreen.
- `createCodeHighlighter(engineURL, createWorker?)` returns a callable service with `destroy()`. The default page service starts one worker lazily. Queue entries carry cancellation signals; aborting the active Prism work terminates its worker and advances queued jobs. Old worker responses/errors cannot publish into the new job. A five-second watchdog terminates pathological work and reports failure while source remains visible. This is an original responsiveness choice, not an observed reference timeout.
- `prism-worker.ts` calls upstream `tokenize`, converts tokens to source ranges, and sends no HTML. It ignores unknown language IDs safely. Both main and worker paths avoid evaluating note-provided text as code.

## Performance and ownership

Unchanged document/tree snapshots reuse extracted fence bodies, so selection-only refresh does not repeatedly copy long code strings. Live discovery seeks intersecting syntax branches using the existing incremental Markdown tree; offscreen unrelated fences are not highlighted. A fence containing the viewport is inspected in full so multi-line strings and comments retain grammar context. Nested quote/list CodeText segments retain individual source maps, avoiding quote-prefix highlights or source rewrites. Token marks are emitted only where they intersect visible ranges. Duplicate visible code shares work; leaving the visible set aborts unused jobs. Document changes invalidate source-keyed requests, and late completions cannot repaint stale source.

Reading uses IntersectionObserver when available and starts immediately only where that API is absent. Tokenization runs outside the main thread, but extracting a visible large fence and painting many tokens still costs proportional work. The timeout bounds one engine job's wall time, not whole-application latency. No claimed native frame-rate, large-note benchmark or full Prism/reference grammar equivalence follows.

Code stays in the parent note's source/history/selection model. Hidden fence decorations expose atomic marker ranges for native movement without inventing caret positions. Async callbacks never dispatch stored source or selection. Clipboard actions stop their own event only; failed copy does not mutate the note. UI timers and queued highlighting belong to the view/surface and must not survive destruction.

## Indexed selection-refresh follow-up

A follow-up found that reusing extracted bodies alone still left two whole-block costs on every refresh: constructing a language-plus-full-code map key and visiting every token in a fence that intersected the viewport. The cached fence now retains its key and direct highlight-job reference. Selection-only updates reuse both; changed document/tree snapshots reacquire the current source and job. Jobs leaving the visible ownership set are still aborted, and an aborted job cannot be revived through the cached reference. Work cancelled before its microtask begins never starts the highlighter.

`CodeTokenIndex` builds a balanced range index once when a highlight result arrives. Each subtree records its maximum token end, so a query skips unrelated prefixes even when token ranges overlap. Visible source segments are also reached with binary search before converting the visible window to code offsets. Only intersecting token/segment pairs are emitted; overlapping visible ranges deduplicate those pairs. The exact token source spans, marker reveal, copy contracts, pointer/IME freeze and history semantics are unchanged. Active-search reveal results are cached by the existing immutable query and fence snapshot rather than rescanning the same large body on selection changes.

Two counted-work tests cover this change. An index of 100,000 ranges, including a range spanning the entire body, finds a narrow tail window with fewer than 70 token-array reads. An actual CodeMirror view containing a 12,000-line fence and two overlapping narrow windows stays below 100 token-array reads across selection plus explicit refresh, makes at most four indexed queries, emits at most eight candidate visits, and keeps one highlighting job until source changes. A real edit invalidates the cached source and starts the new job. These counts exclude initial parsing, source extraction, index construction, DOM measurement and Prism work; they are algorithmic regression bounds, not frame-time or native performance claims. Tests run serially on the constrained development machine.
