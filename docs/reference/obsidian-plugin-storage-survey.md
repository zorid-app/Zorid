# Top 100 Obsidian plugins: file storage and synced-record benefits

Research snapshot: 2026-10-21. This is evidence for an architecture discussion, not an approved plugin API or S3 implementation plan.

## Method and limits

Rank the currently listed community plugins by the official cumulative `downloads` field, descending, with plugin ID as the tie-breaker. Both [registry](https://github.com/obsidianmd/obsidian-releases/blob/4708e9188c8aaccebe806e55ab60c1d4c308e2f2/community-plugins.json) and [statistics](https://github.com/obsidianmd/obsidian-releases/blob/4708e9188c8aaccebe806e55ab60c1d4c308e2f2/community-plugin-stats.json) were retrieved from commit `4708e9188c8aaccebe806e55ab60c1d4c308e2f2` at 2026-10-21T13:29:25Z. The catalog contained 9,270 entries; rank 100 had 240,503 downloads. This is download-based popularity, not active users, unique installations or current growth. Core, delisted, private and manually distributed plugins are excluded. Age and release/update behavior can influence cumulative totals.

All 100 first-party README snapshots were screened. Selected candidates received targeted source/documentation audits; this is not a full code/dependency/runtime audit of every plugin. README URLs use mutable HEAD; captured content SHA256 values are retained. Selected deep evidence uses commit-pinned sources where available; some implementation/docs URLs track mutable main/master/HEAD branches. Closed-source implementations and documentation gaps remain explicit.

Here, **synced database** means logical plugin records replicated through a deliberate sync protocol, with SQLite a possible local implementation. Copying live SQLite/WAL files is a different mechanism and is not established as safe by this research. Record identity, deletion, conflicts, transactions, schema versions and E2EE still need design. A database engine alone supplies none of the cross-device merge policy.

The question is benefit, not necessity. We count material workloads beyond ordinary small preference files; per-setting merge convenience could benefit almost any plugin. Classification reflects the inspected workload and architectural inference, not a measured speedup, a proven current conflict or a requirement that authors adopt a DB.

| Primary class | Count | Meaning |
| --- | ---: | --- |
| F | 74 | Files/configuration fit the demonstrated workload; no compelling generic record-sync benefit established in the inspected scope. Includes shared file artifacts. |
| L | 10 | Strongest DB role is local/rebuildable indexing or query acceleration. Compatible derived artifacts may still be worth sharing. |
| R | 12 | Plausible durable user-record sync benefit; strength varies from actual relational tables to small, optional histories. Files remain possible alternatives. |
| O | 4 | Durable operational/replication state benefits; does not establish a generic plugin-content database need. |

One primary class keeps the table countable. Hybrid roles are described below and in the retained detailed assessments. F is not proof that no database could ever help; R is not proof that the plugin currently uses or requires a synced database.

## Cases that materially inform the decision

### make.md (#33): direct existing SQLite example

Pinned code exports sql.js SQLite bytes into `.space/context.mdb`, `views.mdb` and `commands.mdb`. Nondefault tables accept user-authored rows independent of Markdown; schema/view/command definitions are durable too. Default contexts also contain file-derived members, so those caches must be distinguished. [SQLite writer](https://github.com/make-md/makemd/blob/cb9ca900d419ac9294d90adfed4140ad0a9675f2/src/adapters/mdb/db/db.ts#L342), [row creation](https://github.com/make-md/makemd/blob/cb9ca900d419ac9294d90adfed4140ad0a9675f2/src/core/react/context/ContextEditorContext.tsx#L495), [adapter](https://github.com/make-md/makemd/blob/cb9ca900d419ac9294d90adfed4140ad0a9675f2/src/adapters/mdb/mdbAdapter.ts).

**Inference:** logical per-row/schema mutations could avoid whole-binary-file replacement conflicts when devices edit independent records. This is the clearest actual database-backed content case in the sample. It is not evidence that copying `.mdb` files already provides conflict-safe record sync. Per-record portable files or exported representations remain possible alternatives.

### Leaflet (#87): user-created map objects

Map serialization saves mutable markers/overlays and drawn shapes; persistence rewrites map entries in plugin JSON data, with an optional configured JSON copy. Note/frontmatter-derived markers are a separate source. [map serialization](https://github.com/javalent/obsidian-leaflet/blob/a26e36bd5d2bdfb3f930562f427241327d306e6e/src/map/map.ts#L1307-L1321), [persistence](https://github.com/javalent/obsidian-leaflet/blob/a26e36bd5d2bdfb3f930562f427241327d306e6e/src/main.ts#L475-L534).

**Inference:** independently editable marker/shape records could preserve unrelated offline edits and deletes more cleanly than replacing one whole map/settings object. GeoJSON/JSON per map/object or field-aware file merging is also viable. Object identity and same-object conflict behavior still need explicit rules; no observed conflict rate is claimed.

### Smart Connections (#22): durable feedback alongside derived embeddings

The inspected pin/hide actions persist user feedback keyed by source/target connection through source-item saves. That feedback is different from regenerable similarity scores and vector data. [hide action](https://github.com/brianpetro/obsidian-smart-connections/blob/3bfe2b259fda93d7935ffb5d530fc8e99ba90c34/src/actions/connections-list-item/hide.js), [pin action](https://github.com/brianpetro/obsidian-smart-connections/blob/3bfe2b259fda93d7935ffb5d530fc8e99ba90c34/src/actions/connections-list-item/toggle_pinned.js).

**Inference:** small logical feedback records could sync independently of expensive, model-specific derived artifacts. A sidecar file is another reasonable representation. The underlying smart-sources storage backend was not exhaustively audited, and no current network-synced SQL implementation is claimed.

### Fantasy Statblocks (#74): a user-managed entity library

User/imported creatures are persisted in `settings.monsters`; the active save path calls Obsidian `saveData`. The bestiary separately combines built-ins and note-derived ephemeral entries. [user creature mutations](https://github.com/obsidian-ttrpg-community/fantasy-statblocks/blob/f248f4af8a3d748c2f64534f15e01c2d846e8b12/src/main.ts#L337-L380), [active persistence](https://github.com/obsidian-ttrpg-community/fantasy-statblocks/blob/f248f4af8a3d748c2f64534f15e01c2d846e8b12/src/main.ts#L304-L334), [bestiary separation](https://github.com/obsidian-ttrpg-community/fantasy-statblocks/blob/f248f4af8a3d748c2f64534f15e01c2d846e8b12/src/bestiary/bestiary.ts#L39-L53).

**Inference:** per-creature records can support independent edits, imports and deletions without rewriting the whole library. YAML/JSON or note files per creature can serve the same portability goal. The source establishes durable user entities, not SQL necessity or a reproduced sync defect.

### Copilot (#9), Claudian (#11): conversation/session metadata

Copilot saves conversation Markdown and also keeps a JSON session index containing session/backend identity, user titles, recent access, projects and deletion tombstones. Its current V4 semantic-search architecture uses external Miyo; old embedded-vector-DB descriptions should not be applied uncritically. [conversation persistence](https://github.com/logancyang/obsidian-copilot/blob/0d6833362d3eaaa393437de8d4647d5fad063f04/src/agentMode/session/AgentChatPersistenceManager.ts), [session index](https://github.com/logancyang/obsidian-copilot/blob/0d6833362d3eaaa393437de8d4647d5fad063f04/src/agentMode/session/AgentSessionIndex.ts), [current search architecture](https://github.com/logancyang/obsidian-copilot/blob/0d6833362d3eaaa393437de8d4647d5fad063f04/docs/vault-search-and-indexing.md).

**Inference:** durable conversation curation/deletion history is a possible record-sync workload, independently of derived AI indexes. Claudian is another conditional conversation/session candidate, but some provider histories live outside the vault: syncing plugin metadata alone does not make a provider session resumable on another device. Provider processes, executable paths and credentials require separate device ownership. [Claudian inspected source](https://github.com/yishentu/claudian/blob/96854b448b6af39a19d42b5a97093efb6c57c3be/src/app/storage/SessionStorage.ts).

### Spaced Repetition (#45), Better Word Count (#43), and smaller history cases

Spaced Repetition currently writes schedules into Markdown comments/frontmatter and also has plugin JSON state. Per-card review/schedule mutations are a plausible record workload, but stable card identity, review ordering and concurrent scheduling remain policy questions. [schedule writer](https://github.com/st3v3nmw/obsidian-spaced-repetition/blob/3d5079f3bcd54531b084040d1c0178f15f681510/src/data/data-store/notes-data-store/notes-data-store.ts#L74), [storage documentation](https://github.com/st3v3nmw/obsidian-spaced-repetition/blob/main/docs/docs/en/data-storage.md).

Better Word Count's optional historical statistics are written as JSON; present word totals can be rebuilt from notes, historical activity cannot. Per-device/day event records could merge better than a single shared aggregate, but the collection feature is optional and disabled by default in the inspected settings. This is a weaker benefit case. [historical statistics writer](https://github.com/lukeleppan/better-word-count/blob/044c1bd1e60c9f4880e55d7e9656076d6af5bd07/src/stats/StatsManager.ts#L42).

Thino review continuity, Reminder mute state, Dice Roller history and Another Quick Switcher history are conditional smaller candidates in the R count, not equal-strength endorsements. Thino's current closed-source implementation is assessed through maintainer documentation/changelog, with unknown internal keys/current sync coverage. Small histories may be better served by ordinary sidecar files or deliberately device-local policy.

## Cases supporting file-backed content and local indexes

- **Dataview (#3), Datacore (#80), Omnisearch (#17), Notebook Navigator (#27):** the central query/navigation/index role is derived from vault content. A local database can accelerate it without becoming a second authoritative user-content store. [Dataview](https://raw.githubusercontent.com/blacksmithgu/obsidian-dataview/HEAD/README.md), [Datacore inspected source](https://github.com/blacksmithgu/datacore/blob/1a83c5b6ed95fe88179212b3867978af54cc00d9/src/index/persister.ts#L17-L76), [Notebook Navigator storage architecture](https://github.com/johansan/notebook-navigator/blob/ede7a1b06cdb282beb8767e8f18e209630f58d94/docs/storage-architecture.md).
- **TaskNotes (#14), Day Planner (#31):** task/time-entry properties and actual clock logs are stored in notes/YAML. Those logs are durable content, not disposable indexes. A future explicit concurrent-session workload could motivate finer-grained sync, but the current features do not establish a need to move them out of files. [TaskNotes inspected source](https://github.com/callumalpass/tasknotes/blob/971e5c9a67661210bd71483ff7f6e5a35047ac3c/docs/features/time-management.md), [Day Planner clock logs](https://github.com/ivan-lednev/obsidian-day-planner/blob/9c483b364d2cd663a336baa427f287c36222c9b8/src/util/props.ts#L25).
- **Full Calendar (#60), Media Extended (#67):** file-backed event/media models provide useful counterexamples to inferring database necessity from a rich feature UI. External calendars/provider state and locally cached media artifacts are separate concerns; current Media Extended internals are not fully public. [Full Calendar source](https://github.com/obsidian-community/obsidian-full-calendar/blob/9601cb51b2636d5e83f82d839e47610ec576e258/src/calendars/FullNoteCalendar.ts#L218-L268), [Media Extended documentation](https://mx.aidenlx.site/docs/v4/concepts/media-notes).
- **Text Extractor (#84):** its first-party README explicitly supports syncing extracted-text JSON cache files so mobile can use results although it cannot run extraction. This corrects an overly broad claim that all derived data should remain local. Sharing expensive or unavailable-to-recipient results can be valuable; this implementation already demonstrates a file-artifact solution. [cache and sync documentation](https://github.com/scambier/obsidian-text-extractor/blob/7c6ce7746d1f66fe0813665fd45a24fe15815dca/README.md#cache--sync).
- **Self-hosted LiveSync (#28), Remotely Save (#12), Git (#5), Readwise Official (#96):** operational journals, transfer/import progress and replication histories serve a different role from plugin-owned user content. Replica/device ownership and provider checkpoints cannot simply be merged as generic user records. [LiveSync architecture](https://github.com/vrtmrz/obsidian-livesync/blob/ce0524d49f4e1c840689d83d3f8f18fce383effb/docs/tech_info.md), [Remotely Save inspected source](https://github.com/remotely-save/remotely-save/blob/34db181af002f8d71ea0a87e7965abc57b294914/src/localdb.ts), [Readwise inspected source](https://github.com/readwiseio/obsidian-readwise/blob/6a29ca237d4e10b8154e7988ff34710ec742551e/src/main.ts#L41-L92).

## Implication for Zorid

Keep the accepted note-backed first-party direction for tasks, work blocks and time entries. These findings support leaving room for optional structured sidecar records for plugins with actual entity/history workloads; they do not authorize a general plugin framework or force any first-party feature into a synced SQL store.

The useful primitive is conflict-aware logical document/record synchronization. SQLite can implement local persistence/querying; portable JSON/YAML files can represent many of the same records. A concrete in-scope consumer should justify the added contract and merge/versioning work. Selectively shared derived artifacts are a separate capability from authoritative record storage.
