# Isolated plugin loader foundation

This original implementation is runnable against host-supplied services and original test fixtures. It is not connected to Zorid's production workspace, does not implement Obsidian's App, and has not run any external community plugin. No reference implementation or assets are included.

## Boundaries and host contract

`src/plugins/module-resolver.ts` preserves the supplied namespace objects, including the existing `Plugin` constructor. The host must pass the very same CodeMirror module imports used by its editor. Audited current specifiers and deprecated aliases return those objects; deprecated aliases emit a diagnostic. Missing known shared modules fail explicitly instead of silently loading another package copy. Unknown modules delegate only to the supplied native resolver, or return `null` in the separately selected desktop mobile-emulation mode. This does not establish actual Capacitor module behavior. Legacy CodeMirror API shims remain unimplemented.

The `obsidian` namespace is supplied by the host. The resolver does not create a partial object masquerading as the complete API. It checks that its `Plugin` property is the existing shared constructor. The fixture namespace only contains the implemented primitives and is explicitly test-only.

`src/plugins/manifest.ts` parses JSON, binds `dir` to the discovery directory supplied by the host, and normalizes missing/reserved authors. Its field/type validation is intentionally stricter than the permissive discovery observed in the reference. Direct loader calls retain the exact supplied manifest object. Directory access authorization and normalization belong to host I/O; the loader only requests the fixed `main.js` and `styles.css` filenames.

Runtime policy separately checks community-plugin enablement, an allowlist/boolean policy, desktop-only status and an optional host incompatibility callback. Minimum app version enforcement is **opt-in**: the bounded reference trace did not establish a universal minimum-version rejection for already installed plugins. Installation/update version selection, manifest discovery, release-specific exclusions, saved enabled IDs and configuration writes are not implemented here. The numeric dotted-version helper is not full semver.

`src/plugins/loader.ts` receives the real app/service object, resolver, policy callback, text reader and style-mount callback. It never accesses a vault or global application directly. CommonJS accepts `module.exports = PluginSubclass` and a truthy `default` export, and checks the constructed object against the shared `Plugin`. App and manifest identity are retained. The default evaluator uses `new Function` with an encoded `plugin:` source URL. This runs selected code in the host realm; it is **not a sandbox**, an installation mechanism or a permission boundary. A host can supply an evaluator when its execution environment needs another mechanism.

The instance is visible through `getPlugin` before its asynchronous `load` finishes. Optional CSS is read after load; the host mounts it before custom CSS and returns a disposer. The loader awaits the optional user-enable hook only for an explicit user enable. Repeated successful loads return the same instance. Per-plugin queues serialize load/unload/reload, including unload requested during an asynchronous hook; unrelated plugin IDs remain independent. Lifecycle hooks must not await a queued lifecycle operation on their own plugin ID, which would depend on the current hook completing. Policy is rechecked after asynchronous stages and before evaluation, construction, loading and style mounting. Changing the captured manifest ID or directory rejects the load while preserving the manifest object's identity. Policy revocation does not cancel arbitrary code already executing; the loader attempts cleanup when control returns.

## Deliberate failure policy and limits

On a load, CSS or user-enable failure, the loader attempts `plugin.unload`, releases any successfully mounted CSS, removes its manager entry and preserves errors. Unload likewise releases CSS and removes manager state even if plugin cleanup throws. This is a deliberate Zorid policy, **not reference rollback parity**: no such rollback was visible in the audited reference enable catch. The style-mount callback must undo any partial insertion before throwing because no disposer has been returned then.

The existing audited `Component` stops cleanup when a callback throws. The loader cannot promise that subsequent callbacks or registrations were released. A test demonstrates that boundary rather than claiming transactional cleanup. Constructor/module-evaluation side effects before a valid Plugin exists also cannot be rolled back. The loader cannot cancel a hook that never settles. Async child hooks retain the existing Plugin lifecycle behavior and are not awaited by that base implementation. Persistent enablement, data-directory delegation, markdown/editor registries, actual App/Vault/Workspace constructors, CSS propagation to popouts and native runtime behavior still need production integration and verification.

## Evidence and verification

The implementation uses the previously retained REA evidence described in [plugin API reference](plugin-api-reference.md), E3 `ev_a023c82af045a4b5acedab1eab958db521c3828491a6320c1f7ee85152573b37`, for the 1.14.4 artifact SHA-256 `958ce57fe22f87fdf121546e46dfccd9c8ee971ce3fd8f801d60d4ece39a2df9`. This pass reread the decoded source character ranges 2945601–2946198 (resolver), 2955475–2957009 (load/unload), and 2959155–2960293 (enable gates/failure). These are static observations, not measured reference execution; the prior semantic graph limitations remain.

Eighteen focused tests in `tests/plugin-loader.test.ts` pass with `node --test --test-concurrency=1 tests/plugin-loader.test.ts`. They cover namespace/alias and constructor identity, a fixture-created real CodeMirror StateField accepted by the shared EditorState, direct/default CommonJS exports, manifest validation and policy, mutable identity and async policy revocation, invalid modules, optional styles, registered-command cleanup, throwing cleanup/compatibility flags, failure aggregation and async load/unload ordering. The combined loader and existing lifecycle pass has 38 tests. Targeted strict TypeScript checking passes for the three new modules and the loader tests. No full suite, production build, native application, mobile runtime or external community plugin was run in this isolated pass.

The CodeMirror test establishes package/extension identity in the test process. It does not establish registration into or removal from an active production editor; that requires the real workspace extension service and a separate integration fixture.
