## Findings and minimal corrections

1. **High: encryption atomicity is overstated.** [Draft:41](/Users/ctk/orca/workspaces/Zorid/managed-data-foundation/docs/managed-data/internal-contract-draft.md:41) says state, operation ID and “outgoing encrypted work” commit atomically, conflating durable authored work with later sealing. Replace with: “For synced collections, one local transaction commits record causal state, exact operation/replay identity and durable authored payload/outbox intent; local/cache collections create no outbound work. Encryption may follow this durable commit. Before first transmission, persist the chosen exact ciphertext atomically with its sealed status; every retry reuses those bytes. A failed seal leaves retriable pending intent, not lost data or a false sync acknowledgment.” Include rebuildable projection and durable change-sequence update in that same local commit, or explicitly mark projection pending against a causal revision; never acknowledge an inconsistent query projection. This matches existing [family_ledger.rs:348](/Users/ctk/orca/workspaces/Zorid/managed-data-foundation/crates/zorid-store/src/family_ledger.rs:348) authored storage and separate sealing, without requiring crypto/network waits inside transactions.

Minimal addition: “One transaction commits authenticated exact-wire receipt/dedupe, record causal state or explicitly retained unresolved state, projection/change sequence and the expected shared relay cursor advance; recheck scope, schema compatibility and plan preconditions at commit. Unsupported family rejection advances no cursor; durable unresolved acceptance requires an explicit observable policy.” Do not implement a second record-only progress stream or call local checkpoint CAS after saving. Existing [family_store.rs:453](/Users/ctk/orca/workspaces/Zorid/managed-data-foundation/crates/zorid-store/src/family_store.rs:453) illustrates this boundary. Mere download or an error log does not establish durable ingestion.

Keep the Phase 0 internal first-party scope, and do not claim namespace separation is a sandbox. Main accepted plan lines59–69 correctly distinguishes note/Types/Base files from work blocks, occurrence state and durable provider operations; no conflicting SQL note authority found.

4. **Medium: version compatibility and resource rejection are underspecified.** [Draft:32](/Users/ctk/orca/workspaces/Zorid/managed-data-foundation/docs/managed-data/internal-contract-draft.md:32) distinguishes three versions but omits feature release version and local storage layout version. Minimal addition: “Do not promise recovery from the winning CRDT projection alone; demonstrate durable retained authored/conflict history after restart/GC, or document the unsupported case before adopting the policy.” Explicit restore should name the tombstone/generation it supersedes; otherwise an old concurrent edit or delayed delete can affect the restored record unexpectedly.
