1. Field patches and container identity.
Scenario: seeded record A changes title while B changes color; expect both. Contrast replacing one JSON object under a record key: expect arbitration of the entire object, demonstrating lost independent fields. Also start two peers without a seeded nested record and independently insert MapPrelim at the same record ID; different parent objects may compete even when child keys differ. Provisional choice: stable root field map per record/document, or a seeded shared nested map with explicitly handled create collisions; never recreate the parent map for each patch. One-document-per-record avoids parent creation conflict but costs document/routing overhead and does not provide cross-record transactions. Test simultaneous create of the same ID and edits arriving before create; do not claim deep merging simply because both values are maps.

2. Same-field conflicts and invariant groups.
Scenario: A/B concurrently set title to distinct strings, then one writer causally replaces the converged value; swap actor IDs to expose ID arbitration. Provisional choice: native map scalar arbitration is acceptable only for explicitly declared low-risk fields. Scheduling conflicts need retained candidate operations/causal metadata or a separate conflict representation; a losing map value alone is insufficient evidence for conflict UI/recovery. Store start/end/timezone as one atomic non-shared value and concurrently replace the entire tuple, rather than independently merging components into an impossible interval. Tradeoff: edits to separate tuple components can conflict, but tuple validity survives arbitration. Test invalid local patches without mutation, set-vs-unset, null-vs-absent, equal concurrent values, three-way conflict, and merged cross-field invariants; a local Yrs transaction does not preserve arbitrary invariants across concurrent transactions.

3. Sets.
Scenario: both add the same member; distinct adds; observed remove versus concurrent re-add; remove after observing both adds; duplicate operation retry; label rename with stable option ID. Provisional choice to evaluate: observed-remove/add-wins set with unique add tags and removals of observed tags, with membership deduped by stable member ID. A concurrent unseen add survives; a later observed remove clears it. Tradeoff: tag/tombstone growth and eventual compaction protocol. Compare a member-ID map against these expectations before accepting it as an equivalent implementation; a JSON array replacement loses concurrent additions, and a Y.Array is a sequence rather than inherently a uniqueness-enforcing set. Bound tags in fixtures; design safe growth/compaction separately.

4. Record delete versus edit.
Scenario: A deletes record while offline B edits title/adds a set member; replay delayed edits after restore. Provisional choice: monotonic logical deletion of a record generation, with preserved payload and ordinary patches unable to clear deletion; explicit restore creates a new generation linked to the old one. This yields delete-wins visibility with recoverable concurrent edits, at the cost of retained tombstones and explicit restoration semantics. Do not implement delete by removing the nested record map and assuming content remains recoverable. Compare physical map removal to expose behavior, but do not mistake its convergence for the selected product policy. Test delete-before-create delivery, duplicate delete, stale patch after restore, two deletes and explicit undo; distinguish field-unset from record deletion.

5. Unknown fields.
Scenario: newer peer seeds unknown scalar, tuple and set fields; older peer changes a known field, then unsets another known field; newer peer updates unknown data concurrently. Unknown values must survive merged state, snapshot replay and canonical export. Provisional choice: patch only declared compatible fields, retain supported-but-unknown values without deserialize/reconstruct replacement, reject writes that invent or change unknown fields. Missing fields must not trigger persisted default rewrites. Tradeoff: storage/export must retain opaque data the older UI cannot interpret. Unknown schema fields are distinct from unknown wire types or unexpected shared roots: the latter remain bounded validation failures or retained unresolved envelopes, not blanket acceptance. Test whole-record stale replacement rejection and unsupported-type quarantine without partial accepted state mutation.

6. Schema versions.
Scenario: v1 offline edits a stable field while v2 adds an optional field/renames its label; both operations survive without rewriting the v2 field away. Separate destructive case: v2 changes a field type while v1 submits its old-type patch; require an explicit supported translator or retained unresolved operation, never blind application/drop. Provisional v1 scope: additive optional fields, stable IDs and labels; no arbitrary migration callbacks and no scalar schemaVersion=max() shortcut that relabels untranslated values. Record semantic version and operation origin version must remain distinguishable from actor clocks and wire version. Test two peers applying the same migration identity, duplicate delivery, migrate-before-old-edit and old-edit-before-migrate, plus unknown future version rejection/retention. Deterministic callback output alone does not deduplicate CRDT inserts. Defer a general migration engine until required, while preserving these incompatibility cases as acceptance fixtures.
